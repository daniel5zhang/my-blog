# Daniel实验室 - 三类资产同步规则 SOP

> 目标：把 Daniel实验室 当前已经确认的三类资产边界，固化成 OpenClaw 后续可执行的操作规范。

## 一、适用范围
本 SOP 适用于 Daniel实验室 当前的三类资产：
1. 运营线内容
2. OpenClaw 产品化内容
3. Daniel实验室 网站资产

每次 OpenClaw 执行与这三类资产相关的任务时，都必须按本 SOP 判断：
- 这项资产属于哪一类
- 应该写到飞书、GitHub，还是双留存
- 执行后至少要回写什么痕迹

---

## 二、三类资产定义与边界

### 1. 运营线内容
**定义**：
围绕日常运营推进的动态资产，包括：
- 选题池
- 内容日历
- 待改写池
- 待发布池
- 审核记录
- 反馈复盘
- 试运行排期与审核动作

**边界**：
- 属于“活状态”与日常协作面
- 未来默认由飞书主控台承接
- GitHub 保留镜像模板、规则和关键里程碑快照

**默认存储规则**：
- 飞书：主维护面
- GitHub：双留存（镜像模板、规则文档、关键快照）

### 2. OpenClaw 产品化内容
**定义**：
围绕 Daniel实验室 如何借助 OpenClaw 持续建设出来的产品化资产，包括：
- Agent 职责边界
- 自动化边界
- 网站母稿到分发 SOP
- 产品建设流程日志
- OpenClaw 相关样板流程
- 能力建设路线与阶段留痕

**边界**：
- 属于能力建设、流程机制、产品化沉淀
- 不是日常运营台账，也不是站点正文资产

**默认存储规则**：
- 飞书：需要双留存时可同步关键规则与阶段记录
- GitHub：主沉淀层

### 3. Daniel实验室 网站资产
**定义**：
直接构成 Daniel实验室 网站本体与已发布内容的资产，包括：
- 站点源码
- 页面模板
- 已发布文章
- 正式前端配置
- 已进入站点的内容文件

**边界**：
- 这是 Daniel实验室 的正式公开站点基线
- 不以飞书为主控台，不在飞书中做主维护

**默认存储规则**：
- GitHub：主维护面
- 飞书：原则上不同步正文与源码，只允许记录运营引用信息

---

## 三、触发条件与责任 Agent

### 运营线内容
**触发条件**：
- 新增选题
- 更新排期
- 新增 / 修改待改写状态
- 审核状态变化
- 发布后新增反馈复盘

**责任 Agent**：
- `main`：冻结标准、做最终判断
- `canmou`：补选题与研究输入
- `creator`：母稿与改写草稿状态更新
- `yunying`：排期、待发布、反馈复盘维护

### OpenClaw 产品化内容
**触发条件**：
- 新增 SOP
- 调整 Agent 职责
- 明确新的自动化边界
- 形成新的阶段性建设结论
- 样板流程升级为稳定方法

**责任 Agent**：
- `main`：主责冻结与回写
- `jinhua`：涉及工程化、自动化、部署时协同

### 网站资产
**触发条件**：
- 新增 / 修改正式文章
- 修改站点页面或源码
- 修改站点结构、配置、布局、视觉或内容 schema

**责任 Agent**：
- `main`：范围冻结与验收
- `jinhua`：工程实现
- `creator`：正式内容生产

---

## 四、飞书动作 / GitHub 动作 / 回写条件

### 1. 运营线内容
**飞书动作**：
- 更新主控台 6 张表中的状态、排期、审核、复盘

**GitHub 动作**：
- 当结构、规则、字段、模板发生变化时，更新：
  - `docs/operations/bitable-mirror/`
  - `docs/operations/bitable-sync-rules.md`
  - 对应台账 / 规则文档

**回写条件**：
- 字段结构变了
- 某轮试运行经验升级为长期规则
- 某项排期 / 审核机制正式定型

### 2. OpenClaw 产品化内容
**飞书动作**：
- 仅当需要进入主控台协同或阶段汇总时，记录关键阶段结论

**GitHub 动作**：
- 必须更新 `docs/openclaw/` 下对应 SOP、日志、样板流程文档

**回写条件**：
- 机制正式冻结
- 形成可复用规则
- 产生新的产品建设阶段里程碑

### 3. 网站资产
**飞书动作**：
- 不同步源码和正文
- 如需在飞书引用，只记录链接、状态或运营引用信息

**GitHub 动作**：
- 必须在仓库内完成内容或代码变更
- 必须更新 `CHANGELOG.md`

**回写条件**：
- 每次提交都要回写更新记录
- 任何正式内容进入站点后，都以 GitHub 为准

---

## 五、只在飞书 / 只在 GitHub / 双留存

### 只在飞书维护
- 日常排期临时变化
- 审核中的即时备注
- 负责人临时调整
- 复盘中的临时观察草稿

### 只在 GitHub 沉淀
- 站点源码
- 已发布文章正文
- 页面结构与配置
- 正式 SOP 文档
- 长期产品建设日志

### 需要双留存
- 运营线主控台结构
- 运营镜像模板
- 审核规则
- 试运行方案
- 阶段性关键运营结论
- OpenClaw 产品化中的关键规则与阶段总结

---

## 六、每轮执行后的最低留痕要求
每次 OpenClaw 执行与三类资产相关的任务后，至少必须完成以下留痕：

### 通用最低要求
- 更新 `CHANGELOG.md`
- 若规则发生变化，更新对应 SOP / README 索引
- 若运营结构变化，更新飞书镜像模板或同步规则

### 运营线任务执行后至少更新
- 飞书主控台对应表的状态
- 若形成稳定规则，回写 GitHub 对应文档

### OpenClaw 产品化任务执行后至少更新
- `docs/openclaw/` 下对应文档
- 若新增阶段里程碑，更新产品建设日志

### 网站资产任务执行后至少更新
- GitHub 中对应源码 / 正式内容文件
- `CHANGELOG.md`

---

## 七、执行禁区
- 不得把网站正文与源码直接迁成飞书主维护资产
- 不得把本地私有草稿 / diary 混入运营资产或产品化资产
- 不得在未确认范围时，同时改飞书、GitHub、站点三层资产
- 不得在执行后不留痕

---

## 八、执行顺序（标准动作）
每次涉及资产同步时，OpenClaw 默认按以下顺序执行：
1. 判断任务属于哪一类资产
2. 判断是飞书、GitHub 还是双留存
3. 在主维护面执行变更
4. 在另一侧做必要回写
5. 更新 `CHANGELOG.md`
6. 更新相应 README / SOP / 日志
7. 再提交或汇报
