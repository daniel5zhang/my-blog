# 多Agent架构与职责

## 背景与目标
如果 OpenClaw 产品化长期依赖一个“大而全”的主代理，系统最终一定会遇到上限：上下文过长、边界漂移、责任不清、交接困难、维护成本越来越高。Daniel实验室 当前采用的是“总控收口 + 专职角色协同”的多 Agent 架构，目的不是制造流程复杂度，而是让不同类型的工作拥有稳定归属和稳定输出。

本篇的目标，是把 Daniel实验室 当前已形成稳定事实的多 Agent 架构，整理成正式章节，重点回答：
- 为什么 OpenClaw 产品化不能退回单点包办；
- 当前各角色分别负责什么、不负责什么；
- 协作链路如何形成闭环；
- 角色边界如何保护正式资产与执行质量。

## 设计原则

### 1. 总控的价值在于收敛，不在于包办
`main` 的首要职责，是冻结目标、判断边界、路由任务、验收结果，而不是长期亲自做完所有事情。总控如果直接包办，会让角色系统退化成“一个人临时救火”，协作结构就失去意义。

### 2. 角色存在的意义是稳定输出类型
多 Agent 不是多几个名字，而是让每类输出都有清晰归属：
- 研究类输出归研究角色；
- 内容类输出归写作角色；
- 工程与结构类输出归工程角色；
- 运营推进与状态维护归运营角色；
- 总控负责范围冻结与最终收口。

只有输出类型稳定，模板、索引、SOP 和交接才能稳定。

### 3. 职责边界比能力上限更重要
Daniel实验室 当前强调的是：角色即使“会做”，也不应越界去做所有事。边界的重要性高于能力的广度，因为边界直接决定系统是否会失控。

### 4. 协作目标是降低单点脆弱性
多 Agent 架构的价值，不在于让流程更长，而在于把复杂度拆开：
- 决策不被实现细节淹没；
- 内容不被结构动作污染；
- 运营推进不被代码实现绑架；
- 正式资产可以被不同角色接力维护。

## 当前角色结构

### `main`：总控
`main` 负责：
- 冻结阶段目标、范围与验收标准；
- 判断当前任务应该交给谁；
- 汇总各角色结果并做最后取舍；
- 审核边界、口径、风险与正式表达。

`main` 不应长期代替专职角色完成其本职工作，否则会破坏多 Agent 架构本身。

### `canmou`：参谋
`canmou` 负责：
- 调研与信息架构判断；
- 选题与方向建议；
- 优先级和阶段判断；
- 竞品观察与趋势扫描。

它的作用是降低“做什么”的盲目性，不直接承担结构工程或正式长文母稿的主责。

### `creator`：笔杆子
`creator` 负责：
- 长文母稿写作；
- 平台稿改写；
- 标题、摘要、表达收敛；
- 把零散输入升级为可读的正式内容。

它的边界包括：
- 不拿平台稿反推母稿；
- 不把私有草稿混入正式资产；
- 不替代总控冻结边界；
- 不承担网站工程与结构修复主责。

### `yunying`：运营官
`yunying` 负责：
- 发布节奏；
- 运营台账与日历；
- 推荐位、专题推进、状态维护；
- 飞书主控台与部分索引状态的更新。

它的职责是让体系会“推进”，而不仅仅会“写”。

### `shequ`：社区官
`shequ` 负责：
- 反馈与评论整理；
- 社区问题回流；
- 用户关注点提炼。

虽然本轮重点不在社区执行，但该角色说明当前体系已经为外部反馈回流预留正式接口。

### `jinhua`：进化官
`jinhua` 负责：
- 站点与工程结构实现；
- 自动化与复杂技术动作；
- 文档结构修复、节点归位、复杂同步；
- 将规则工程化、脚本化、结构化。

在 OpenClaw 产品化手册层面，`jinhua` 更重要的职责是“把规则真正落成结构”，而不是只停留在建议层。

## 当前协作链路

### 协作链路一：产品化规则建设
1. `main` 冻结阶段范围；
2. `jinhua` 处理结构、路径、复杂落地；
3. `main` 回看结果并收口；
4. GitHub、Wiki、Bitable 三层同步。

### 协作链路二：正式内容生产
1. `canmou` 判断方向与重点；
2. `creator` 输出正式母稿；
3. `main` 审核是否进入正式资产；
4. `yunying` 维护推进状态；
5. 必要时 `jinhua` 处理结构与同步动作。

### 协作链路三：维护与迭代
1. `main` 判断属于日常维护、周维护还是里程碑维护；
2. `yunying` 回写状态与索引；
3. `jinhua` 处理结构问题与复杂同步；
4. `main` 更新正式口径与留痕。

## 为什么边界必须明确

### 1. 防止任务漂移
没有边界，任务会不断膨胀。一个原本只是“补正文”的任务，可能被临时扩展成结构重做、工程重构、渠道扩张，最终失控。角色边界的第一作用，就是把任务约束在冻结范围内。

### 2. 防止责任悬空
边界清楚后，问题才能被快速定位：
- 是总控没有冻结清楚；
- 是结构没有落地；
- 是内容没有收口；
- 还是索引与状态没有回写。

### 3. 防止单点依赖成为常态
如果所有事情最后都回到一个上下文极长的主代理身上，系统的复杂度只会继续累积。多 Agent 架构的价值，是把复杂性拆解给合适角色，而不是继续压给单一入口。

## 配置、工具与正式接口

### 1. 角色模板已经形成正式接口
当前仓库已形成 `role-execution-templates.md`。这意味着角色不再只是理念上的分工，而已经拥有可操作接口：
- 输入要求；
- 执行步骤；
- 最低留痕要求；
- 飞书与 GitHub 动作口径。

### 2. 索引层是角色推进的状态接口
很多角色动作未必每次都要改正文，但通常都应更新状态。`OpenClaw产品迭代` 作为索引层，承担了角色推进的正式记录接口。

### 3. GitHub 是角色规则的长期沉淀层
只要某个角色推动了结构、规则、模板或正式正文变化，就不应只停留在飞书上下文中，而必须回写 GitHub。这是协作长期有效的基础。

## 风险与边界

### 1. 最大风险：临时突破角色边界
当前多 Agent 架构最怕的，不是角色“不够聪明”，而是在压力下角色边界被临时突破：
- 运营角色开始决定技术边界；
- 内容角色开始替代总控定范围；
- 工程角色在边界未冻结时直接进入大规模实现。

### 2. 角色命名不等于正式职责
是否能长期承担某类工作，不取决于角色名字，而取决于是否已经形成稳定事实、模板和留痕规则。本篇只记录已稳定的正式职责，不记录临时帮忙式动作。

### 3. 本篇不覆盖的内容
本篇不讨论：
- 站点代码细节；
- EdgeOne 部署；
- 外部发布执行；
- 具体运营台账逐条内容；
- 单次任务的临时分配细节。

## 与其他文档的关系
- 与 `agent-roles.md`：后者是职责边界摘要，本篇是正式主干正文。
- 与 `role-execution-templates.md`：本篇说明为什么这样分工，模板说明具体怎么执行。
- 与 `automation-boundaries.md`：本篇回答“谁做什么”，自动化边界回答“哪些动作允许自动做”。
- 与 `openclaw-product-overview.md`：总览给出产品化总体框架，本篇聚焦角色协同结构。
- 与 `product-build-log.md`：建设日志记录角色协作在各阶段如何实际发生。

## 维护方式
本篇应只在以下情况更新：
- 新增长期角色；
- 角色边界发生稳定变化；
- 某项临时职责升级为正式规则；
- 协作链路形成新的长期稳定模式。

若只是某次具体任务由谁执行，不应频繁修改本篇，而应优先回写阶段日志、索引层或具体执行样板。
