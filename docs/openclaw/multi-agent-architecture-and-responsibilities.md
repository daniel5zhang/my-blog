# 多Agent架构与职责

## 背景与目标
OpenClaw产品化如果只有“一个很能干的主代理”，最终一定会遇到上限：上下文过长、边界混乱、责任漂移、执行不可交接。Daniel实验室 当前采用的是“总控 + 专职角色协同”的多 Agent 架构，其目的不是把任务分得更复杂，而是把能力拆成更稳定、更可管理的责任面。

这篇正文要解决的问题，是把 `agent-roles.md` 里相对简明的职责说明，升级成一篇正式手册章节：不仅说明谁负责什么，更说明为什么这样拆、怎么协作、什么不能越界、怎样在产品化体系里持续运转。

## 设计原则 / 核心判断

### 1. 总控不是包办，而是收敛
在 Daniel实验室 的 OpenClaw 体系里，`main` 的价值不是自己把所有活干完，而是：
- 冻结目标
- 判断边界
- 选择谁来做
- 汇总结果
- 把关验收

如果总控直接长期代替所有专职角色，系统会退化成单点劳动，而不是多 Agent 协作。

### 2. 专职角色的意义在于稳定输出类型
多 Agent 不只是“多几个人名”，而是让每个角色形成稳定的输出类型：
- 有的人负责研究
- 有的人负责表达
- 有的人负责运营推进
- 有的人负责工程与结构

一旦输出类型稳定，模板才能稳定，交接才能稳定，索引与留痕才能稳定。

### 3. 职责边界比能力范围更重要
很多系统出问题，不是因为角色不会做，而是因为角色做了不该做的事。例如：
- 运营角色去改站点代码
- 内容角色直接把平台稿当母稿
- 工程角色在未冻结边界前先进入实现

Daniel实验室 当前通过角色边界，把这些高频失控点提前封住。

## 当前多 Agent 架构

### `main`：总控
`main` 负责的是整个系统的方向与边界，具体包括：
- 冻结阶段目标、范围与验收标准
- 决定当前阶段是否进入执行
- 汇总各 Agent 结果并做最终取舍
- 审核结构、口径、对外表达边界

它不是默认执行者，而是默认协调者。

### `canmou`：参谋
`canmou` 负责研究与判断，典型职责包括：
- 研究选题方向
- 提供信息架构建议
- 做优先级判断
- 做竞品观察与趋势扫描

它的价值，是降低系统在“做什么”这件事上的盲目性。

### `creator`：笔杆子
`creator` 负责把原始信息组织成正式内容，典型职责包括：
- 网站母稿写作
- 平台改写
- 内容表达收敛
- 把零散信息升级成可发布文本

它的边界也很明确：不能跳过母稿直接把平台稿当源头，不能把私有草稿混进正式资产。

### `yunying`：运营官
`yunying` 负责运营推进与节奏管理，典型职责包括：
- 设计发布节奏
- 维护内容日历
- 维护订阅、推荐位与专题更新节奏
- 维护飞书主控台状态

它对系统的价值，是让产品化体系不只会“写”，还会“推进”。

### `shequ`：社区官
`shequ` 负责反馈整理与用户问题回流，典型职责包括：
- 收集评论与反馈
- 提炼常见问题
- 把读者关注点回流给选题与专题

尽管本轮重点不在社区动作，但这个角色的存在说明体系预留了面向外部反馈的接口。

### `jinhua`：进化官
`jinhua` 负责结构、工程与自动化，典型职责包括：
- 网站代码实现
- 页面结构调整
- 搜索、订阅、评论、部署、自动化脚本
- 技术文档与维护性改进

在 OpenClaw 产品化手册层面，`jinhua` 更重要的职责是：
- 处理结构问题
- 落地复杂文档路径
- 处理节点 move 与结构修复
- 把规则工程化

## 协作不是并列劳动，而是接力
多 Agent 架构真正有效，不在于大家都很忙，而在于每个人在合适的时间接手合适的任务。

### 典型协作链路一：规则建设
1. `main` 冻结边界
2. `jinhua` 落地结构和路径
3. `main` 回看并固化口径
4. GitHub / Wiki / Bitable 同步

### 典型协作链路二：内容生产
1. `canmou` 提供选题与方向判断
2. `creator` 产出母稿与改写稿
3. `yunying` 维护排期和发布状态
4. `main` 把关是否进入正式资产层

### 典型协作链路三：产品化维护
1. `main` 判断本轮属于日常维护、周维护还是里程碑维护
2. `yunying` 维护状态与索引变化
3. `jinhua` 处理结构、节点、复杂同步
4. `main` 收口并更新正式口径

## 角色边界为什么重要

### 1. 防止任务漂移
没有边界，任何任务都会越做越大。多 Agent 架构的第一价值，是让任务在进入执行前就先被收敛。

### 2. 防止责任悬空
边界清楚之后，任何一个阶段出问题，都能很快判断：
- 是目标没冻结
- 是结构没落地
- 是状态没回写
- 是内容没收口

这样系统才可维护。

### 3. 防止“一个人临时救火”成为常态
如果系统长期依赖一个超长上下文的大代理处理所有事务，任何扩张都会变脆。多 Agent 架构的意义，就是把复杂性拆开，而不是把复杂性压给单一角色。

## 关键流程与工具说明

### 1. 角色模板是正式协作接口
当前已经形成 `role-execution-templates.md`，它让角色边界不只是一段说明，而是可直接执行的模板。对于产品化体系来说，这一点非常关键，因为它把“职责”升级成了“可操作接口”。

### 2. Bitable 是角色推进的状态层
很多角色协作并不一定都要改正文，但通常要更新状态。`OpenClaw产品迭代` 及飞书主控台其他表，就是角色推进的状态层。

### 3. GitHub 是规则层
角色如果推动了结构、规则、模板变化，就不能只停留在飞书里，必须回写 GitHub。这保证协作不是只存在于当前对话上下文中。

## 常见问题 / 风险 / 边界

### 1. 多 Agent 会不会把事情搞复杂？
如果没有边界，会；但在 Daniel实验室 当前体系里，多 Agent 的目标不是制造流程，而是降低单点失控。它让每类输出有明确归属，而不是所有问题都混在一起。

### 2. 为什么 `main` 不直接做完所有事情？
因为总控最重要的价值是判断，不是体力劳动。如果总控长期下场包办，边界、验收、分工都会失真。

### 3. 当前这套角色架构最怕什么？
最怕角色边界在压力下被临时突破。一旦 `yunying` 开始写结构规则，或 `creator` 开始决定产品边界，体系就会重新失控。

### 4. 当前明确不做什么？
本篇不讨论：
- 站点前端实现细节
- EdgeOne 部署动作
- 真实对外发布执行
- 运营台账本身的逐条内容

## 与其他文档的关系
- 与 `agent-roles.md` 的关系：那篇是角色边界摘要，本篇是正式章节化表达
- 与 `role-execution-templates.md` 的关系：本篇解释为什么这样分工，模板负责具体怎么执行
- 与 `automation-boundaries.md` 的关系：本篇回答“谁来做”，自动化边界回答“哪些事允许自动做”
- 与 `asset-sync-sop.md` 的关系：本篇解释角色如何协作，资产同步 SOP 说明成果最终落到哪层

## 后续维护方式
本篇应在以下情况更新：
- 新增长期角色
- 角色边界发生稳定变化
- 某个角色的职责从临时安排升级为正式规则
- 多 Agent 协作链路形成新的稳定模式

如果只是某次具体任务由谁执行，不应频繁改这篇正文，而应优先写入阶段日志、索引层或具体样板。
