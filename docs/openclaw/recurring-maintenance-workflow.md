# OpenClaw产品化手册周期性维护执行流程

## 背景
正式手册已经成型，但如果没有固定的周期性维护动作，正文层、索引层和 GitHub 备份层很快会失同步。本流程用于把日常、周度、里程碑级维护动作收敛成一致执行口径。

## 目标
- 规定按日 / 按周 / 按里程碑应该执行什么维护动作
- 明确哪些动作更新 Wiki，哪些更新 Bitable，哪些只更新 GitHub
- 明确 `main` / `jinhua` / `yunying` 的职责分工
- 统一最小留痕要求与授权失败时的停、记、重试方式

## 一、按日维护

### 目标
- 保证索引层状态与当日实际推进一致
- 不让小变化堆积成结构性失真

### 典型动作
- 更新 `OpenClaw产品迭代` 中的状态、阶段、下一步
- 补充新增知识库正文的链接
- 对当天新增的关键规则变化做 GitHub 简要留痕

### 更新位置
- **Wiki**：只有当日确实新增了正式正文或正文结论变化时才更新
- **Bitable**：状态、阶段、下一步、链接变化优先更新这里
- **GitHub**：当日如形成稳定规则、结构变化或正式里程碑，更新对应文档与 `CHANGELOG.md`

## 二、按周维护

### 目标
- 检查三层结构是否仍然一致
- 把一周内零散变化收敛为正式记录

### 典型动作
- 复核 Wiki 正文是否有新增但未进索引层的条目
- 复核 Bitable 是否存在链接缺失、状态滞后、阶段不准
- 复核 GitHub 镜像 / README / SOP 是否需要同步更新
- 检查一级主题与关键二级正文的挂载关系是否仍清晰

### 更新位置
- **Wiki**：补正式周度结论、长期新增章节
- **Bitable**：统一修正索引项状态与链接
- **GitHub**：补镜像、README、同步规则、`CHANGELOG.md`

## 三、按里程碑维护

### 目标
- 把阶段成果升级为正式可复用资产
- 把产品化建设结果沉淀成可交付、可复刻、可销售材料

### 典型动作
- 新增正式章节或重大重写
- move 二级正文到正确一级主题下
- 更新产品建设日志、维护 SOP、同步规则、镜像说明
- 更新阶段里程碑与复刻口径

### 更新位置
- **Wiki**：新增 / 重构正式正文
- **Bitable**：新增或升级索引记录，补阶段、状态、链接、下一步
- **GitHub**：必须同步更新镜像、README、SOP、`CHANGELOG.md`

## 四、角色分工

### `main`
- 负责判断本轮属于日常维护、周维护还是里程碑维护
- 负责冻结边界、确定该改 Wiki / Bitable / GitHub 哪一层
- 负责最终留痕与口径一致性把关

### `jinhua`
- 负责涉及结构、节点 move、自动化、规则工程化的部分
- 负责复杂同步路径、结构性修复、执行链路排障

### `yunying`
- 负责索引层状态、阶段、下一步的持续维护
- 负责把运营视角下的推进变化及时反映到 Bitable
- 不负责改正式手册规则，不负责改站点代码

## 五、每次执行的最小留痕要求
每次周期性维护后，至少满足以下条件之一：
1. 已真实完成一项 Wiki / Bitable / GitHub 变更
2. 若发生正式规则变化，必须更新 GitHub 文档与 `CHANGELOG.md`
3. 若发生结构变化，必须更新镜像文档
4. 若只是状态变化，至少更新 Bitable 索引层，并在必要时补 GitHub 简要记录

## 六、遇到 `need_user_authorization` 的处理方式

### 停
- 立刻停在当前资源动作上
- 不继续伪造后续完成状态

### 记
- 记录当前卡在哪类资源：
  - Wiki 读取 / 创建
  - Bitable 写入 / 更新
  - 节点结构管理
- 记录当前目标对象、动作与错误信息

### 重试
1. 等用户完成对应授权
2. 重试原动作
3. 原动作成功后再继续后续链路
4. 最后统一回写 GitHub
