# 模型、渠道与飞书协同

## 背景与目标
OpenClaw 产品化的长期价值，并不等于某个模型本身的能力，也不等于某个聊天入口是否顺手。真正决定系统能否持续运行的，是模型、任务渠道、飞书正式层与 GitHub 留痕是否构成闭环。Daniel实验室 当前已经验证：如果模型只负责回答、渠道只负责传话、飞书只负责临时存放，那么系统仍然只是一个“偶尔能帮忙的助手”；只有把这三者组织成稳定工作流，OpenClaw 才具备产品化意义。

本篇要说明的，是当前已完成事实下的三类核心问题：
- 模型在产品化体系里承担什么角色；
- 渠道为什么不是一个简单“消息壳”；
- 飞书为什么成为当前阶段最关键的正式协作与沉淀面。

## 设计原则

### 1. 模型不是产品本身，而是产品引擎之一
OpenClaw 的产品价值，不在于“接了哪个模型”，而在于模型是否被正确放进结构中。当前模型承担的核心职责包括：
- 理解任务边界与约束；
- 组织复杂上下文与正式表达；
- 生成结构化结果；
- 辅助做路径判断与工具路由。

模型很重要，但它必须工作在正式结构之内，而不是取代结构本身。

### 2. 渠道是协作入口，不是附属外壳
渠道决定的是：
- 用户如何发起任务；
- 任务如何被补充限制；
- 执行过程如何被反馈；
- 授权、确认与收口如何发生。

因此渠道不是“消息能发出去”就够了，而是必须能支撑产品化协作路径。

### 3. 飞书的价值在于把结果升级成资产
如果结果只留在聊天里，就没有长期价值。飞书当前最重要的作用，是把任务结果沉淀为：
- Wiki 正文；
- Bitable 索引；
- 可导航结构；
- 可追踪状态。

### 4. 当前阶段强调协同稳定，不强调渠道扩张
Daniel实验室 当前边界已冻结：
- 不把站点代码、EdgeOne、内容发布等范围混入本轮；
- 不对外扩展尚未稳定的多渠道能力；
- 重点说明已经稳定成立的模型、渠道与飞书协同闭环。

## 模型在当前体系中的真实职责

### 1. 正式内容组织者
模型当前最稳定的价值之一，是把分散的信息整理成正式资产：
- 主干正文；
- SOP；
- 模板；
- 样板；
- 日志与总结。

这类工作不是简单生成，而是需要在上下文中持续遵守边界、保持术语一致、识别哪些内容已经是事实、哪些内容仍未落地。

### 2. 结构判断辅助者
模型当前不仅写文，还参与判断：
- 哪个主题适合承接新正文；
- 该更新 Wiki 还是索引层；
- 何时需要回写 README、镜像和 `CHANGELOG.md`；
- 哪些结论应升级为正式规则，哪些只应进入日志。

### 3. 边界执行器
Daniel实验室 当前很多任务都有明确边界，例如：
- 不碰站点代码；
- 不碰 EdgeOne；
- 不做内容发布；
- 只做指定批次正文。

模型在执行中必须不断重复这些边界，并据此约束自己的输出。这是产品化中的关键能力，而不只是“遵守指令”这么简单。

## 渠道在当前体系中的真实职责

### 1. 飞书会话是当前主触发入口
当前最稳定的任务入口，是飞书会话。它的价值不只是“方便聊天”，而是：
- 可持续下达任务；
- 可追加细化要求；
- 可在同一协作环境中完成授权与确认；
- 可直接连接 Wiki 与 Bitable 正式层。

### 2. 渠道决定交互与回路成本
没有正式渠道时，很多动作会变成：
- 先聊天；
- 再手工找文档；
- 再手工改表；
- 再手工补链接；
- 再补日志。

而当前飞书协同的意义，在于让任务、正文、索引、反馈尽可能停留在同一操作面内完成，降低上下文切换成本。

### 3. 渠道也必须有边界
虽然 OpenClaw 可以连接更多渠道，但 Daniel实验室 当前并未把所有渠道都纳入正式产品化范围。原因很明确：在主路径尚未完全稳定前，扩渠道只会带来更多不确定性。当前真正稳定的，是“模型 + 飞书正式层 + GitHub 备份层”的闭环。

## 飞书在产品化体系中的正式位置

### 1. Wiki 正文层
飞书 Wiki `OpenClaw产品化手册` 当前承载：
- 一级主题；
- 主干正文；
- SOP；
- 模板；
- 执行样板；
- 长期可阅读资产。

它的职责是让结果不只存在于生成过程，而是成为可培训、可复用、可交接的正式内容。

### 2. Bitable 索引层
`OpenClaw产品迭代` 当前承载：
- 记录名称；
- 内容类型；
- 阶段；
- 责任角色；
- 摘要；
- GitHub 文档链接；
- 状态；
- 下一步；
- 备注与知识库链接。

索引层的价值，是让正式资产具备可检索、可盘点、可推进的管理接口。

### 3. 授权与协作现实
飞书资源可能按资源类型分别触发授权。Daniel实验室 当前已经多次遇到授权相关场景，因此正式口径必须承认：
- 授权是协作边界的一部分；
- 授权受阻不等于正文不能先写 GitHub；
- 正文、索引、回写动作应尽量分离，避免单点阻塞影响全部链路。

## 模型、渠道、飞书如何形成闭环

### 1. 模型负责组织与判断
模型接收范围、背景、边界与阶段目标，输出结构化结果，并辅助判断内容应进入哪一层。

### 2. 渠道负责触发与反馈
渠道承接用户需求、补充限制、确认结果、授权提示和收尾反馈，使整个过程具备连续协作上下文。

### 3. 飞书负责正式沉淀
任务结果进入 Wiki 正文层和 Bitable 索引层后，才真正从“回答”升级为“资产”。

### 4. GitHub 负责长期留痕
当结果已进入正式层，就必须回写 GitHub 文档、镜像与 `CHANGELOG.md`，保证体系具备回滚和审计能力。

当前 Daniel实验室 已经形成的，不是简单的“模型生成内容”，而是：
**模型组织 → 渠道触发 → 飞书沉淀 → GitHub 留痕** 的正式工作闭环。

## 核心配置、工具与流程

### 1. 模型层配置关注的是职责，不是参数炫技
当前正式文档只记录已经稳定成立的模型职责和协作方式，不虚构尚未固化的模型参数或复杂调优策略。

### 2. 渠道层配置关注的是默认主路径
当前主路径已经明确：飞书会话是主要协作入口，飞书正文层与索引层是主要正式承载面，GitHub 是长期备份层。

### 3. 飞书工具配置关注的是分层使用
- 正文工具用于正式长文；
- 节点工具用于结构归位；
- Bitable 工具用于索引层更新；
- 不把单一工具当成“什么都能做”的万能入口。

## 风险与边界

### 1. 最大风险：结果停留在对话中
如果模型已经完成判断，但没有进入 Wiki、Bitable 或 GitHub，产品化体系就会重新碎片化。当前必须坚持“正式结果必须落层”。

### 2. 把飞书当唯一真相源
飞书适合协作，但不是唯一长期源头。没有 GitHub 备份层，正式资产的版本连续性和审计能力都会下降。

### 3. 把索引层当正文层
Bitable 的职责是索引，不是长文表达。把完整论述挤进索引层，会直接破坏正式资产的可读性和可维护性。

### 4. 本篇不覆盖的内容
本篇不讨论：
- 站点实现细节；
- EdgeOne 部署动作；
- 尚未形成稳定事实的多渠道外扩；
- 对外内容分发与平台运营执行。

## 维护方式
本篇只应在以下场景更新：
- 新的稳定协作渠道进入正式范围；
- 模型在产品化中的职责发生稳定变化；
- 飞书正文层、索引层或授权边界出现结构性变化；
- 模型、渠道、飞书与 GitHub 之间的正式闭环发生实质调整。

如果只是新增一篇正文、补一条索引或完成一次授权，不应频繁重写本篇，而应优先更新对应专题正文、索引与建设日志。
