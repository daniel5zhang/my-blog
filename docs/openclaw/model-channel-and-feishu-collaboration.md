# 模型、渠道与飞书协同

## 背景与目标
OpenClaw产品化不是单纯的“模型接好了”或“消息能发出去”就结束。真正决定系统能否长期运行的，是模型、渠道和协作面是否被组织成统一工作流。

Daniel实验室 当前的真实建设已经说明：
- 模型能力决定生成与执行质量
- 渠道决定系统如何被触发、被使用、被感知
- 飞书决定正式正文、索引状态和协作链路如何落地

如果这三者彼此脱节，OpenClaw 最终只会变成一个偶尔能回答问题的助手；只有把它们组织起来，才会成为真正的产品化系统。

本篇的目标，是把 Daniel实验室 当前已验证过的模型使用、渠道协作和飞书落地逻辑，整理成正式手册正文。

## 设计原则 / 核心判断

### 1. 模型不是产品本身，而是产品引擎的一部分
OpenClaw 的产品价值，并不等于某个模型本身的能力。模型更像引擎：
- 负责理解和生成
- 负责结构化执行
- 负责在复杂上下文中维持判断

但真正让产品成立的，是外层的结构、流程、工具路由和留痕机制。

### 2. 渠道不是“发消息的壳”，而是协作入口
不同渠道决定了 OpenClaw 以什么形式参与工作。当前 Daniel实验室 的实际协作中，飞书是最关键的正式协作入口，因为它同时承载了：
- 当前对话
- Wiki 正文层
- Bitable 索引层

这使得飞书不仅是一个聊天入口，更是正式产品化体系的操作面。

### 3. 飞书的价值在于把输出从“回答”升级为“资产”
如果只在聊天里回答，再强的模型也很难沉淀长期价值。飞书的价值，是把回答转化为：
- 正式正文
- 索引记录
- 可导航的知识结构
- 可追踪的推进状态

### 4. 当前阶段强调“协同稳定”，而不是“渠道扩张”
Daniel实验室 当前已明确冻结边界：
- 不扩到真实内容发布
- 不碰 EdgeOne
- 不把站点代码与产品化正文混层

所以本篇重点不是列举所有可能渠道，而是说明当前已经形成稳定事实的模型 / 渠道 / 飞书协同方式。

## 模型层的真实作用

### 1. 帮助形成正式文档
当前多轮建设已经证明，模型最稳定的价值之一，是把零散阶段结果、规则片段和执行经验，整理成正式文档、模板、样板与主日志。这类工作对上下文整合、结构组织和表达一致性要求很高，模型在这里是核心引擎。

### 2. 帮助执行结构化同步
模型不仅写文，也参与判断：
- 该更新 Wiki 还是 Bitable
- 哪条记录应该新增，哪条应该 update
- 哪份文档应做正式正文，哪份只做规则摘录
- 哪个主题最适合承接新正文

这说明模型在产品化体系中承担了“结构判断器”的角色。

### 3. 帮助控制边界
当前 Daniel实验室 多轮任务都有明确边界，例如：
- 不碰站点代码
- 不碰 EdgeOne
- 不碰内容发布
- 只做某几篇正文

模型在这里不只是生成内容，而是帮助系统在执行过程中持续遵守边界。这是产品化能力的重要组成部分。

## 渠道层的真实作用

### 1. 当前核心渠道是飞书会话
飞书会话是当前最重要的任务触发入口。原因不是“消息方便”，而是：
- 它可以持续下达任务
- 它可以承接授权
- 它可以直接连接飞书知识库与多维表格
- 它可以让结果从对话直接进入正式资产层

### 2. 渠道决定交互成本
如果没有飞书这类渠道，很多动作会退化为：
- 先聊天
- 再手动找文档
- 再手动改表
- 再手动补记录

而现在的协同方式，可以让很多工作在同一上下文中直接完成。这种低切换成本，是产品化系统的重要优势。

### 3. 渠道边界也必须明确
虽然 OpenClaw 支持多种能力，但当前 Daniel实验室 并未把所有外部渠道都纳入正式产品化范围。原因很简单：产品化初期更重要的是让主路径稳定，而不是让边界无限扩张。

## 飞书协同的正式结构

### 1. Wiki 正文层
Wiki 正文层承担的是“正式表达”。
当前已经用于承载：
- 手册一级主题
- SOP
- 执行流程
- 模板
- 真实样板
- 正式主干正文

其意义在于：所有关键结果最终都能沉淀成可阅读、可培训、可交付的资产。

### 2. Bitable 索引层
Bitable 索引层承担的是“正式检索与状态管理”。
当前已经用于承载：
- 标题
- 内容类型
- 阶段
- 状态
- 责任角色
- GitHub 链接
- 知识库链接
- 下一步

它让手册不只是“文档堆”，而是一个可管理资产库。

### 3. 飞书授权是协作现实的一部分
当前已经多次遇到 `need_user_authorization`，这说明飞书协同不是完全无摩擦的。不同资源类型会分别触发授权，因此正式协作必须把授权视为系统边界的一部分，而不是把它当作偶发 bug。

## 模型、渠道、飞书三者如何形成闭环

### 1. 模型负责组织与判断
模型把任务需求、规则约束和现有资产整理成可执行结果。

### 2. 渠道负责触发与反馈
用户通过飞书对话发起任务、追加限制、确认结果，渠道提供连续交互面。

### 3. 飞书正式层负责资产沉淀
最终结果不应只停留在对话中，而应进入：
- Wiki 正文层
- Bitable 索引层

### 4. GitHub 负责长期备份
当结果足够正式，就必须回写 GitHub 文档与 `CHANGELOG.md`，确保体系具备长期可追溯性。

这四者合在一起，才构成 Daniel实验室 当前真实成立的产品化工作流。

## 常见问题 / 风险 / 边界

### 1. 为什么不直接把所有内容都只放在飞书里？
因为飞书适合协作，但不应成为唯一长期源头。没有 GitHub 备份层，正式资产会缺少可回滚与可审计能力。

### 2. 为什么不把“模型选择”写得更细？
因为当前仓库和正式资产里真正稳定成事实的，不是某个模型参数细节，而是“模型在产品化体系里承担什么角色”。本篇严格基于已发生事实，不虚构未稳定的能力配置。

### 3. 当前最大的协同风险是什么？
最大的风险是：
- 对话里完成了判断，但没有落到正文
- 正文更新了，但索引没补
- 飞书里改了，但 GitHub 没留痕

这会让产品化体系重新碎片化。

### 4. 当前明确不讨论什么？
本篇不讨论：
- 站点前端代码实现
- EdgeOne 生产部署
- 对外发布执行
- 尚未形成稳定事实的多渠道扩展能力

## 后续维护方式
这篇正文应在以下情况更新：
- 新的稳定协作渠道进入正式产品化范围
- 模型使用方式形成新的长期规则
- 飞书协同层出现稳定结构变化
- 模型、渠道、飞书之间的闭环方式发生实质调整

若只是新增某篇正文、补一条索引或完成某次授权，不应频繁改本篇，而应优先更新相应日志、索引与专题文档。
