# OpenClaw产品化手册后续维护 SOP

## 背景
`OpenClaw产品化手册` 已经从临时文档集合升级为正式知识库结构，当前也已形成：
- Wiki 正文层
- Bitable 索引层
- GitHub 备份层

接下来最重要的不是继续无序扩写，而是把“以后如何维护”固化成统一、可执行、可复用的标准口径。

## 目标
- 固化 OpenClaw 产品化手册的后续维护规则
- 说明什么时候改 Wiki 正文、什么时候只改索引、什么时候要 move 节点
- 统一最小留痕要求、失败排障顺序与禁止事项

## 一、资产分层定义

### 1. Wiki 正文层
承载：
- 正式说明文档
- 长内容手册正文
- 结构化章节内容
- 面向交付、复刻、销售展示的完整表达

### 2. Bitable 索引层
承载：
- 手册核心资产索引
- 知识库链接
- GitHub 文档链接
- 状态、阶段、下一步
- 关键记录的快速查询入口

### 3. GitHub 备份层
承载：
- 主文档与镜像文档
- SOP、README、同步规则、CHANGELOG
- 回滚、备份、审计与长期留痕

## 二、何时新增正文
满足以下任一情况时，应新增 Wiki 正文：
- 出现新的长期主题，已经不适合只写在对话或表格备注里
- 需要形成可交付、可复刻、可销售的正式章节
- 某个领域已经积累出稳定方法论，需要独立成文
- 原有一级主题下新增了一个明确的长期二级主题

## 三、何时只更新索引层
满足以下情况时，可只更新 Bitable 索引层：
- 正文没有新增结构，只是状态、阶段、下一步变化
- 已有文档链接需要补齐或修正
- 某条资产进入“启用 / 持续更新 / 归档”等状态变化
- 只需增强检索与总览，不涉及正文结论变化

## 四、何时需要 move 节点
满足以下情况时，应考虑 move 节点：
- 某篇正文已明确归属到某个一级主题下
- 当前节点仍滞留在根级，影响结构可读性
- 一级主题已经存在，且对应二级正文数量开始增长
- 需要把知识库从“平铺文档”推进到“可管理层级树”

**执行原则：**
- 优先复用现有节点
- 能 move 就 move
- 不为追求好看而复制正文或新建重复文档

## 五、一级主题与二级正文的维护原则

### 一级主题
- 保持在根级
- 作为稳定骨架，不频繁更名
- 每个一级主题负责承接一类长期主题资产

### 二级正文
- 优先挂到对应一级主题下
- 必须围绕明确主题归属，不允许随意漂浮
- 若尚未确定长期归属，可暂留根级，但要尽快收口

## 六、每次更新的最小留痕要求
每次涉及正式手册维护时，至少完成：
1. 该变更对应的 Wiki / Bitable / GitHub 动作之一真实完成
2. GitHub 中至少更新：
   - 对应 SOP / 镜像 / README / `CHANGELOG.md` 中的必要部分
3. 若结构发生变化，必须回写镜像或说明文档
4. 若只是状态变化，至少更新索引层并在 GitHub 留简要记录

## 七、授权失败 / 参数失败的排障顺序

### 1. `need_user_authorization`
排查顺序：
1. 判断当前动作属于哪类资源（表、文档、Wiki 节点）
2. 确认用户是否已完成该资源类型的授权
3. 授权完成后重试原动作
4. 成功后再回写 GitHub

### 2. `field validation failed`
排查顺序：
1. 检查是否漏传关键字段
2. 对 Wiki 节点创建，优先检查 `node_type`
3. 若目标只是创建正文，回退到 `feishu_create_doc(wiki_space=...)`
4. 若目标是结构管理，再继续使用节点工具

### 3. 结构不清或找不到节点归属
排查顺序：
1. 先盘点当前节点清单
2. 识别一级主题是否已存在
3. 判断是 move 还是新增正文
4. 没把握时，先留 GitHub 卡点，不伪造完成状态

## 八、禁止事项
- 不把长正文塞进 Bitable 索引层
- 不为了“看起来完整”而新建重复文档
- 不在未确认归属前随意 move 大量节点
- 不在失败时伪造 GitHub 完成状态
- 不把站点资产、运营内容、OpenClaw 手册正文混层维护
- 不在本轮手册维护任务中顺手处理站点代码、内容发布或 EdgeOne

## 九、后续固定执行顺序
1. 先判断本轮属于正文新增、索引更新，还是节点层级调整
2. 正文新增优先更新 Wiki 正文层
3. 状态变化优先更新 Bitable 索引层
4. 结构变化再处理 move 节点
5. 最后回写 GitHub 备份层与 `CHANGELOG.md`
