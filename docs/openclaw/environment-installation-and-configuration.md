# 环境安装与配置

## 背景与目标
OpenClaw产品化不是“能启动一次”就算完成。真正的难点在于：环境必须可重复准备、配置必须可判断、工具必须知道什么时候该用、什么时候不该用，执行者必须清楚什么是稳定路径，什么是高风险路径。

Daniel实验室 之所以把“环境安装与配置”单独写成正式正文，是因为这部分直接决定了 OpenClaw 到底是一个偶尔能跑的实验环境，还是一个可以长期维护的正式系统。

本篇的目标，不是覆盖所有 OpenClaw 官方文档细节，而是基于 Daniel实验室 当前已经验证过的真实事实，把环境层最关键的安装、配置、运行与排障逻辑整理成一篇正式手册正文。

## 设计原则 / 核心判断

### 1. 先稳定路径，再谈高级玩法
环境层最容易出问题的，不是“功能不够”，而是路径太多、口径不稳。Daniel实验室 当前已经验证出一些更稳定的路径，例如：
- 正式知识库正文优先使用 `feishu_create_doc(wiki_space=...)`
- Wiki 节点结构管理才使用 `feishu_wiki_space_node.*`
- Bitable 写入必须以既有表结构与字段口径为准

这意味着环境配置并不是“把所有工具都打通”那么简单，而是要明确每种场景的默认执行路径。

### 2. 环境配置的目标是降低不确定性
安装不是目的，减少不确定性才是目的。一个好的环境配置，至少应做到：
- 工具能找到正确的执行面
- 角色知道边界
- 飞书授权能被预期管理
- 正文层、索引层、备份层的动作不混淆

### 3. 配置必须服从产品化边界
OpenClaw 可以连接很多系统，但 Daniel实验室 当前阶段并不追求“全都接上”。本轮已冻结的边界包括：
- 不碰 EdgeOne 生产变量
- 不把站点代码与产品化正文混写
- 不把运营台账和手册正文混层
- 不把旧定时任务残留内容继续带入正式资产

因此，环境配置必须服从边界，而不是反过来推动边界扩张。

## 环境层当前真实组成

### 1. GitHub 正式文档工作区
当前 OpenClaw 产品化文档的正式源文件位于：
- `docs/openclaw/`

这里承载：
- 主干规则文档
- 正式手册正文
- 流程、模板、样板
- 产品建设主日志

它是 GitHub 备份层的核心部分。

### 2. 飞书正式层
当前已经形成两类飞书正式层：

#### Wiki 正文层
承载 `OpenClaw产品化手册` 的正式章节，用于：
- 阅读
- 培训
- 导航
- 正式表达

#### Bitable 索引层
承载 `OpenClaw产品迭代` 的索引记录，用于：
- 跟踪每篇正式资产
- 挂知识库链接
- 挂 GitHub 文档链接
- 记录状态、阶段、下一步

### 3. 结构骨架已经稳定
当前已经形成 8 个一级主题的正式结构，说明环境层不仅仅是“工具可用”，而是“结构已经能承载持续写作”。这对后续扩写非常重要，因为后续新增正文都有明确挂载位。

## 安装与配置的核心对象

### 1. 文档层配置
文档层最核心的不是传统意义上的软件安装，而是正式资产承载位的确定：
- GitHub：正式源文件与长期留痕
- Wiki：正式正文层
- Bitable：正式索引层

任何新文档的加入，都要先判断它属于哪层、主维护面是什么、需要同步到哪里。

### 2. 飞书知识库路径配置
在 Daniel实验室 当前口径中，写正式正文的稳定方式是：
- 使用 `feishu_create_doc`
- 显式指定 `wiki_space=7621060014035193021`

这条路径已经通过多轮实践验证。它的意义不是“创建文档”本身，而是建立一条低歧义、低失败率的正式正文写入路径。

### 3. 节点结构配置
如果只是写正文，不必先想节点管理；但一旦进入正式结构维护，节点配置就很重要。当前已验证的关键事实包括：
- `feishu_wiki_space_node.create` 在节点结构场景可用
- 实体节点必须显式传 `node_type=origin`
- `move` 可用于把既有正文归位到一级主题下

这意味着：
- 正文创建路径和节点结构路径必须分离
- 不能把“创建正文”和“管理树结构”混成同一步

### 4. Bitable 字段配置
索引层依赖稳定字段，包括：
- 记录名称
- 内容类型
- 阶段
- 责任角色
- 摘要
- 对应 GitHub 文档
- 状态
- 下一步
- 备注

字段稳定的意义在于：
- 保证每次新增正文后，索引层可以快速补齐
- 保证后续检索时不会因为字段漂移而失真

## 当前推荐执行流程

### 场景一：新增正式正文
1. 先确认该内容是否已经足够形成正式长文
2. 在 GitHub 写正式源文件
3. 查飞书对应主题下是否已有合适正文
4. 没有则创建，有则更新
5. 必要时 move 到对应一级主题下
6. 更新 `OpenClaw产品迭代` 对应索引记录
7. 回写 `CHANGELOG.md` 与必要 README / 镜像说明

### 场景二：只更新索引信息
1. 确认正文结论未变化
2. 只更新状态、阶段、下一步、链接
3. 若未形成结构性规则，不扩写正文

### 场景三：调整知识库层级
1. 先判断归属是否稳定
2. 优先复用现有节点
3. 能 move 就 move
4. 不为追求“树好看”而复制文档

## 常见问题 / 风险 / 边界

### 1. 为什么明明是“环境安装”，却写了很多流程？
因为 OpenClaw 当前环境问题，本质上并不只是“软件装没装”，而是“路径是否稳定、配置是否统一、执行是否知道往哪落”。环境配置如果脱离流程，最后仍然无法复刻。

### 2. `field validation failed` 说明什么？
说明不能把工具表面名称当作真实能力边界。当前已确认，该错误高概率来自 `node_type` 漏传。环境层必须把这种失败经验固化成默认规则，而不是每次重踩。

### 3. `need_user_authorization` 应如何理解？
它不是异常噪音，而是飞书协作环境的现实边界。不同资源类型可能分别触发授权，因此环境配置必须把“授权是多点触发”视为常态，而不是偶发。

### 4. 当前明确不覆盖哪些内容？
本篇不覆盖：
- 站点前端部署细节
- EdgeOne 生产配置
- 内容发布链路
- 与本轮无关的自动化扩展

## 后续维护方式
这篇正文应在以下情况更新：
- 写正文或挂正文的默认稳定路径发生变化
- 节点管理方法发生稳定变化
- 索引层字段结构发生稳定变化
- 环境层边界扩大到新的长期模块

如果只是新增某篇正文、更新某条索引、完成某次授权，不应不断改这篇正文，而应优先更新日志、索引与对应专题页面。
