# 环境安装与配置

## 背景与目标
OpenClaw 产品化的环境层，不等于“把依赖装上就行”。真正决定系统能否长期运行的，是环境、配置、工具路径和协作边界是否形成了可重复的默认口径。Daniel实验室 当前已经验证：环境问题大多不是“功能不足”，而是“路径过多”“角色混用”“配置漂移”“授权预期不一致”。

因此，本篇不是传统意义上的安装教程汇编，而是 Daniel实验室 基于真实已完成事实整理出的环境层正式正文，回答以下问题：
- 当前 OpenClaw 产品化依赖哪些正式承载面；
- 什么才是已经验证过的默认稳定路径；
- 文档、索引、结构管理分别应该落在哪一层；
- 环境层最常见的风险是什么，如何避免。

## 设计原则

### 1. 先稳定默认路径，再考虑高级能力
OpenClaw 工具很多，但产品化环境不追求“全能打通”，而追求“主路径低歧义、低失败率、可交接”。Daniel实验室 当前已经验证的主路径包括：
- 正文优先写 GitHub 源文件，再同步飞书正文层；
- 正文创建优先使用飞书文档工具；
- 节点结构管理与正文创建分离；
- 索引更新独立进入 Bitable；
- 最终统一回写 README、镜像与 `CHANGELOG.md`。

### 2. 环境层的核心目标是降低不确定性
一个好的环境层，不是“功能菜单更多”，而是让执行者始终知道：
- 当前该写哪一层；
- 哪条路径是默认稳定路径；
- 哪些动作需要授权或人工确认；
- 哪些内容不能混写、不能越界。

### 3. 配置必须服从产品化边界
当前阶段已经冻结的边界包括：
- 不碰 EdgeOne 生产变量与部署动作；
- 不把站点代码与产品化正文混层；
- 不把运营台账当成正文层；
- 不把旧定时任务残留继续带入正式资产。

环境层的任务，是让正式范围更稳定，而不是推动范围继续扩张。

## 当前环境的正式组成

### 1. GitHub 备份层
当前正式源文件位于：`docs/openclaw/`。这里承载：
- 主干正文；
- SOP；
- 模板与样板；
- 产品建设日志；
- README、镜像和 `CHANGELOG.md`。

GitHub 的职责不是日常协作面，而是长期备份层、规则层和审计层。

### 2. Wiki 正文层
飞书 `OpenClaw产品化手册` 承载正式正文。它服务于：
- 阅读与导航；
- 培训与交接；
- 正式表达；
- 主题归档与结构管理。

### 3. Bitable 索引层
飞书多维表格 `OpenClaw产品迭代` 承载正式索引。它当前用于维护：
- 记录名称；
- 内容类型；
- 阶段；
- 日期；
- 责任角色；
- 摘要；
- GitHub 文档链接；
- 状态；
- 下一步；
- 备注。

### 4. 结构骨架已稳定
当前手册 8 个一级主题已建立完成。这意味着环境层已经不只是“工具能调”，而是“正式承载位已经确定”。后续新增正文的关键，不再是重新设计结构，而是判断归属并按主路径写入。

### 5. 记忆层基础设施已进入正式环境范围
截至 2026 年 3 月 25 日，OpenClaw 的环境层已经不再只包含 GitHub、Wiki、Bitable 和执行工具，还正式包含以下记忆基础设施：
- 全局 `MEMORY.md`
- 全局 `memory/YYYY-MM-DD.md`
- 各子代理独立的长期记忆与角色日记
- `memorySearch` 索引与检索层
- embeddings provider、cache、chunking 与 reindex 流程

这意味着环境层的职责已经从“把内容写进去”扩展到“保证长期知识可以被稳定恢复与复用”。

## 配置对象与默认口径

### 1. 文档层配置
文档层最重要的配置，不是某个单一参数，而是“该内容属于哪层”。当前默认判断为：
- 面向阅读与培训的长文 → Wiki 正文层；
- 面向检索与推进的状态字段 → Bitable 索引层；
- 面向长期保存与审计的源文件 → GitHub 备份层。

### 2. 飞书知识库配置
当前已验证的关键事实是：
- 飞书正文层已经可以稳定承载主干正文；
- 创建正文与管理节点应拆成两步，而不是混成一步；
- 节点归位是结构动作，不应和正文写作动作混淆。

### 3. 节点结构配置
对于知识库结构，当前默认原则是：
- 一级主题保留在根级，不轻易重排；
- 二级正文归到对应主题下；
- 能 update 的优先 update；
- 需要新增时 create；
- 只有结构归位需要时才 move。

### 4. 索引字段配置
`OpenClaw产品迭代` 的字段口径已经形成稳定事实。当前新增一篇正式正文后，索引层至少应补齐：
- 记录名称；
- 内容类型；
- 阶段；
- 责任角色；
- 摘要；
- 对应 GitHub 文档；
- 状态；
- 下一步；
- 备注（通常放知识库链接与补充说明）。

### 5. 记忆配置对象
当前已经稳定进入正式环境口径的记忆相关配置包括：
- `memorySearch.provider`
- `memorySearch.model`
- `memorySearch.sources`
- `memorySearch.extraPaths`
- `memorySearch.query.hybrid`
- `memorySearch.chunking`
- `memorySearch.cache`

这些配置不再是实验性附属项，而是 Daniel实验室 当前产品化环境的一部分。它们直接决定：
- 哪些正式材料可被召回；
- 主代理与子代理分别看到什么；
- 索引重建与召回质量是否稳定。

## 当前推荐流程

### 场景一：新增主干正文
1. 先在 GitHub 写正式源文件；
2. 根据主题归属同步到对应飞书节点；
3. 更新 `OpenClaw产品迭代` 对应记录；
4. 回写镜像、README 与 `CHANGELOG.md`；
5. 形成 commit 留痕。

### 场景二：只修正文内容
1. 先修改 GitHub 正文；
2. 再 update 飞书对应文档；
3. 若摘要、阶段、下一步发生变化，再更新索引层；
4. 最后决定是否需要补写日志与 `CHANGELOG.md`。

### 场景三：只修结构或节点归位
1. 先确认主题归属稳定；
2. 优先复用既有正文；
3. 通过节点管理工具归位；
4. 若知识库链接变化，回写索引层备注或链接字段。

## 工具与授权说明

### 1. 正文写入工具
正文创建与正文更新已经形成稳定工具路径。当前重点不是“会不会调”，而是写入前必须先明确目标层、归属主题和是否已有旧文。

### 2. 节点管理工具
节点管理工具只在知识库结构场景使用。它的职责是树结构维护，而不是正文内容维护。

### 3. 多维表格工具
多维表格工具用于索引层回写，不用于替代长正文，也不用于承载复杂论述。

### 4. 授权是现实边界的一部分
飞书资源可能按资源类型分别触发授权。当前正式口径是：
- 把授权视为系统边界，而不是偶发异常；
- 不因为授权未完成就跳过 GitHub 正文回写；
- 授权受阻时优先保证本地源文件与日志留痕完整。

### 5. 远端 embedding 端点同样属于环境边界
当前语义记忆已经正式启用，因此 embedding provider 也成为环境层的一部分。它不只是“性能优化项”，而是决定记忆检索是否真实可用的正式依赖。当前口径已经明确：
- provider 要能通过 readiness 检查；
- 模型、端点、chunking 或索引面变化后，应视情况强制重建索引；
- 远端端点短时失败不应导致正式记忆结构回退，但必须保留 reindex 与排障路径。

## 风险与边界

### 1. 最大风险：把“可用”误当“稳定”
很多动作可能偶尔成功，但并不意味着已经形成默认稳定路径。环境层文档只写已验证过、能够复用的事实，不把偶然成功经验包装成正式规则。

### 2. 结构动作与写作动作混淆
正文创建、节点归位、索引补齐如果混成一步，后续排障会非常困难。当前必须坚持分层、分动作执行。

### 3. 表格字段漂移
一旦索引字段在不同阶段随意更名或新增，后续检索、阶段回顾和模板复用都会失真。因此字段结构只允许在必要时做稳定升级，不做临时性漂移。

### 4. 本篇不覆盖的内容
本篇明确不覆盖：
- 站点前端实现；
- EdgeOne 生产配置；
- 内容分发；
- 用户系统、CMS、评论、订阅实现等非当前范围事项。

## 维护方式
本篇只在以下场景更新：
- 默认稳定路径发生变化；
- 节点管理或正文写入规则发生稳定变化；
- `OpenClaw产品迭代` 索引字段结构发生调整；
- 新的长期正式承载面进入产品化范围。

如果只是新增一篇正文、补一条索引或完成一次授权，不应反复改动本篇，而应优先更新日志、索引与对应专题正文。
